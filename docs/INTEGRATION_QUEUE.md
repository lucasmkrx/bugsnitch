# Pull-request inspection

The dashboard's pull-request inventory contains owner-selected inspections. The service can obtain a separate installation token granting one repository read-only access to Pull requests, Issues, Checks, Commit statuses and Contents. Grant these additional read permissions to the App installation before inspecting PRs. Open an existing project with an active GitHub mapping and use the owner API to inspect a numbered PR and its canonical issue. Repositories must match the numeric installation mapping and the configured full name.

```http
POST /api/v1/projects/{project}/pulls/{number}/refresh
Content-Type: application/json

{"issueNumber":12,"version":0}
```

The first inspection takes version 0. Future refreshes use the presented version. The snapshot includes the PR head, current target branch tip, PR and issue state, issue requirements digest, review decision, and count and rollup status of checks on that exact head. A missing rollup, zero reported checks or check results from another commit yields unknown status. The API returns observed timestamps and flags stale snapshots. [GitHub pull-request fields](https://docs.github.com/en/graphql/reference/pulls) · [GitHub check rollups](https://docs.github.com/en/graphql/reference/commits)

An owner with a retained artifact may record its SHA-256 digest and kind, either `independent_review` or `combined_validation`, through `POST /api/v1/projects/{project}/pulls/{number}/evidence` with `version`, `kind` and `reference`. The reference identifies an owner attestation. Retain the referenced artifact and its execution transcript outside this inspector. The server refreshes GitHub first and rejects a changed subject. The version binds the specific head, tested target, ticket contents, plan version, project settings and observed check/review state. A change preserves historical receipts and removes them from current evidence.

The standard inspector reads GitHub. The separately enabled protected-queue operation described below requires configured branch/queue protections, required CI on the combined candidate, verified dependency and policy gates, current scoped decisions and review findings, and knowledge of deployment side effects. A successful rollup on the PR head cannot establish that its combination with another candidate passes. GitHub's merge queue can validate grouped changes against the latest target when its required checks run on merge groups. Eligibility depends on repository ownership, visibility and plan. [GitHub merge queues](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

Protocol fixtures cover repository-scoped read permissions, missing checks, and a check rollup bound to the wrong commit. The PostgreSQL test `TestPostgresInvalidateEvidenceOnSubjectChange` changes the head, base, issue requirements, and project version independently and exercises the stale-write conflict. Follow the [focused test setup](../README.md#verification-and-operations). Run `go test ./internal/github ./internal/integration` with `BUGSNITCH_TEST_DATABASE_URL` pointing to a disposable PostgreSQL database for the persistence test. Actual private-repository access, queue settings and a live merge remain unverified.

In **Pull requests**, the owner can watch an inspected open PR. The background worker refreshes its GitHub checks and reviews at most once every two minutes per PR. Reads stop after a closed or merged observation, when the repository mapping is disabled, or when the owner stops watching. An owner or approver can attach artifact digests and record integration sign-off once GitHub reports approval and passing checks. Sign-off binds the current inspection version, head, target branch and target revision.

After GitHub reports a merge, an owner or approver can record a **Deployment handover** with the environment, immutable build, verification digest and steps for the stakeholder. The receipt records the inspected merge commit and the authenticated approver. Incident verdicts continue to use the incident's own deployment and validation receipts.

## Draft creation

On the originating paired computer, `local-ship` publishes an exact reviewed candidate and waits for the GitHub App to open its draft PR. The runner must already be registered to the project and have GitHub CLI credentials with branch push access. In the dashboard, open the completed attempt, select the target and **Publish the branch with local-ship on the paired computer**, then approve the request. You can also start the command first. It syncs the attempt so the owner can review it in the dashboard.

```sh
bugsnitch local-ship --id "$ATTEMPT" --version "$VERSION" \
  --candidate "$HEAD_SHA" --target main --wait 10m
```

The approval holds the job for this device, report version, candidate and target. Before pushing, the runner checks that GitHub's target still points to the reviewed base and rereads the approval. The owner can withdraw it while the dashboard shows **Awaiting publication**. Once GitHub accepts a branch push, withdrawal can stop the draft while leaving that branch published. The runner confirms publication to the service, the App checks both refs and the issue again, and the command prints the draft PR URL. An immediate dashboard draft request remains available for a branch you already published.

The default foreground wait is ten minutes and the maximum is one hour. Ctrl+C or a timeout ends the local wait. Run the identical command to resume. A completed release is reconciled from the existing outbox entry. After withdrawing a held approval, the owner can review the current attempt and target in the same draft form and authorize it again. Run the command shown beside the renewed approval. The device confirmation and owner withdrawal are bound to that approval version. Once the App job is released, its original receipt remains authoritative for reconciliation. The device credential cannot authorize the draft or change its target.

The owner can run `bugsnitch local-publish --id ATTEMPT --version VERSION --candidate EXACT_SHA` on the originating computer, then request a draft PR. Publication requires GitHub CLI authentication with push access to the configured repository, a current issue, and successful validation and independent review. It creates only the named attempt branch and reconciles a lost reply by reading the remote ref. A different existing tip stops publication. Manual publication remains supported. The runner creates `bugsnitch/{attemptId}`. Review the local commit, diff, validation transcript and independent review before publishing that branch with normal Git credentials. Supply a target branch whose tip still equals the recorded base. Draft creation requires a GitHub App installation with Pull requests write, Contents read and Issues read. The issued token is restricted to the mapped repository. [Pull request creation](https://docs.github.com/en/rest/pulls/pulls#create-a-pull-request)

Submit `POST /api/v1/projects/{project}/attempts/{attemptId}/draft-pr` with the completed report version, effective policy version and target. Optional summary and behavior fields become public PR prose. The authenticated request applies to this candidate and target. Earlier reports that lack the issue revision cannot authorize a draft.

```json
{"version":12,"policyVersion":1,"target":"main","summary":"Correct the comparison at the shipping threshold.","behavior":"Orders of exactly $50 receive free shipping."}
```

The outbox requires a successful validation and independent review on the candidate with zero important findings, an active repository mapping, and project permission to create drafts. Before sending, it locks the local policy and device records, rereads the canonical issue's open state and timestamp, and verifies the published head and target refs. GitHub's create API accepts branch names. A concurrent branch change can still move the PR, so the response records a discrepancy and the inspector must obtain fresh evidence. Draft creation grants no merge readiness. A missing branch remains queued with bounded backoff. A lost create response triggers marker reconciliation against open and closed PRs created by the authenticated App. Review blocked intents in `draft_pr_intents` before any manual retry.

The disposable PostgreSQL test `TestPostgresDraftReconcilesLostResponseAndRejectsStalePolicy` exercises duplicate requests, lost acknowledgement, one canonical PR number and policy revocation using a GitHub protocol fixture. Public GitHub writes require an explicitly configured test repository.

## Queue authorization boundary

A refresh also reads the queue associated with the PR's actual base branch, the existing queue entry's state, position and available head/base commits, and the exact merge commit on a merged PR. It requests the active rules for that target using a repository-scoped token. The persisted snapshot includes a rules digest, presence of a queue requirement, required-check count and number of checks bound to a specific App. Missing rule access remains unknown. Active rulesets, classic branch protection, queue membership, tested revisions and deployment receipts represent distinct observations. [PR and queue fields](https://docs.github.com/en/graphql/reference/pulls) · [Active branch rules](https://docs.github.com/en/rest/repos/rules#get-rules-for-a-branch)

GitHub's enqueue mutation accepts a PR node ID and an expected head OID. Its input also permits queue jumping and a client mutation ID. The published input schema provides no precondition for the destination branch, its rules, a Bugsnitch decision, or deployment effects. GitHub separately allows changing a PR's base branch. Retargeting can preserve the head commit. If the PR switches from an approved disposable branch to another queue-enabled branch before enqueue, a head check alone cannot bind the operation to the approved destination. A database mutex serializes Bugsnitch workers, while GitHub can receive changes from other actors. [Enqueue fields](https://docs.github.com/en/graphql/reference/pulls#enqueuepullrequestinput) · [PR update fields](https://docs.github.com/en/graphql/reference/pulls#updatepullrequestinput)

## Enable protected delivery

In **Pull requests**, refresh the PR, attach independent review and combined validation evidence, and sign off on the displayed revision. The owner can preview queue policy, enter the environment affected by the merge and authorize delivery. The API accepts `POST /api/v1/projects/{project}/pulls/{number}/queue` with `mode` (`observe`, `enforce`, `revoke` or `renew`), `version`, `head`, `base`, `target` and `environment`. Observe calls read GitHub and evaluate eligibility. Each authorization applies to one reviewed revision for one hour. A repeated request returns its previously recorded state. Use the original authorization fields to revoke it before group sign-off. A held or revoked permit on an otherwise unchanged PR can start a fresh integration review with `renew`; attach fresh evidence and obtain sign-off on the new version.

Test the configuration in a disposable organization repository before enabling it for a release. Set `BUGSNITCH_GITHUB_QUEUE_REPOSITORIES` on the server to the comma-separated numeric repository IDs deliberately enrolled for queue operations. Subscribe the GitHub App to `merge_group` events. Configure independent CI on both `pull_request` and `merge_group`. The target must require a merge queue using merge commits and a named required CI check bound to an App distinct from Bugsnitch. Start with one PR per merge group. Selected repositories need installation access for queue reads and writes, checks reads and writes, pull request and contents reads, and repository administration for the rules auditor. The auditor uses a separate repository-scoped token solely to read the detailed ruleset. GitHub discloses the bypass list only to a caller with ruleset write access. No Bugsnitch provider command changes rulesets. [GitHub rulesets](https://docs.github.com/en/rest/repos/rules#get-a-repository-ruleset) · [Required merge-group CI](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

For source changes that require fresh owner approval, install the independently enforced CI policy in the organization. [Required approval workflow](APPROVAL_POLICY.md#require-the-policy-in-protected-ci)

Choose the rule scope that matches the repository.

- For a shared repository, manage a dedicated target such as `staging`. Use one active repository ruleset whose sole condition includes only `refs/heads/staging`, with an empty exclusion and bypass list. It must require the queue and a check named `Bugsnitch queue / staging` from the Bugsnitch App. Reserve this name for this target. On approval Bugsnitch posts the PR-head check and waits for a person or your existing GitHub integration to add it to the queue. Other branches keep their own policies.
- For a dedicated automation repository where Bugsnitch governs every destination, use an active repository ruleset that includes `~ALL`, excludes nothing, has no bypass actors, and requires the merge queue and the App-bound `Bugsnitch queue authorization` check. The worker can then submit GitHub's head-pinned enqueue mutation. Configure branch-creation allowances on required checks and verify the runner can create and update its candidate ref with the actual rules. This topology makes Bugsnitch a gate for every governed PR; use the dedicated target profile for a pilot alongside unrelated work.

The signed group event identifies the installation, repository, target, base, synthetic ref and group SHA. The worker checks the live ref and requires a two-parent synthetic commit whose ordered parents are the authorized base and PR head. Multi-PR groups and unsupported GitHub-generated commit layouts wait for reconfiguration. The worker revalidates the issue, PR review, candidate evidence, project controls, dependency evidence, current sign-off, release order, deployment holds and effective protections before reporting its App check. GitHub enforces the independent group CI and owns the final merge. A lost enqueue acknowledgement triggers reconciliation from queue membership. A missing entry after an uncertain attempt puts the delivery on hold. Once GitHub has accepted the successful group check, cancellation and deployment protection also depend on the repository and its CI configuration.

`TestProtectedQueueReconcilesAndChecksSignedGroup` exercises the actual Rust provider against a loopback GitHub fixture and disposable PostgreSQL, including missing bypass evidence, a retarget, dispatch revocation, a lost enqueue acknowledgement and an incompatible group. Live queue support and any automatic deployment require acceptance in the configured organization.

## Repair a published pull request

On the original registered computer, run `bugsnitch local-steward --id ATTEMPT --version VERSION --candidate CURRENT_PR_HEAD --pr NUMBER`. The command reads failing check names and unresolved, current review threads from the identified GitHub PR using the local GitHub CLI account. It starts a separate, bounded correction attempt on the pinned PR head under the normal registration, admission, file restrictions, validator and fresh independent review. That review sees the complete pull-request diff. The completed original stays inspectable. The existing local issue generation limit permits at most three total attempts including the original and ordinary retries. For regular text conflicts in approved paths, the runner fetches the exact target commit when needed, prepares an isolated merge tree, requires resolution of each marked file, validates, and reviews the complete PR against that target. Structural, binary and out-of-scope conflicts require an owner. Queued and approved PRs stop the steward.

Inspect the new attempt and run `local-publish` with its own version and candidate. A correction can only fast-forward the original PR branch from the exact previously observed head. The receipt includes the previous revision, published revision and an undo command. An ordinary repair supplies a reverse patch. A conflict repair supplies a lease-guarded command to restore only the PR branch to its previous head. Run that command only if you intend to withdraw the entire repair. If a collaborator moved the branch or force updates are disabled, open a follow-up change for review. Add `--post-note` to publish its change and undo receipt to the PR. The steward can monitor an open PR in the foreground with `--watch 45m`; add `--publish` to push reviewed corrections and their undo notes. Repeated unchanged feedback waits for a fresh signal. A new candidate invalidates earlier PR sign-off on refresh. The foreground worker polls every 30 seconds for up to 24 hours. Without `--publish` it returns after producing its first correction for inspection. With `--publish` it follows the corrected head until the time limit, approval, queue entry, or the attempt limit. Ctrl+C stops the foreground worker. Before each push and PR note, paired runners refresh the original device assignment, project pause and scoped plan and policy. GitHub operations already accepted require the receipt's undo procedure.

For example, start a foreground session on the originating device with the exact completed version and candidate shown in `bugsnitch local-list`.

```sh
bugsnitch local-steward --id "$ATTEMPT" --version "$VERSION" --candidate "$HEAD_SHA" \
  --pr "$PR_NUMBER" --watch 45m --publish
```

When a branch diverges, inspect the PR's new head before choosing the next action. Retry an uncertain publication with the same `local-publish --id ... --version ... --candidate ... --post-note` to reconcile the remote ref and existing note. For an unsupported conflict, inspect the two revisions with Git locally and have the owner resolve it on a fresh branch. Validate and independently review the resulting PR head before seeking a new integration sign-off.
