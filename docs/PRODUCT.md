# From issue to verified release

Bugsnitch is a software factory for teams that ship from their own machines. A project maps to one GitHub repository. The workspace holds the plan, decisions and delivery evidence. An assigned computer holds the checkout, runs the agent and validator, and publishes the reviewed candidate when authorized.

## Follow a change

1. **Choose the work.** Start with a canonical GitHub issue or propose new issues in **Plans**. For a production failure, report the observed and expected behavior in **Incidents** or connect Sentry. The owner can promote the incident to a GitHub issue. Record acceptance criteria, dependencies and how to verify each ticket. Publishing new issues and approving the resulting execution plan are separate decisions.
2. **Implement and review.** On the paired computer, use `bugsnitch next --project PROJECT_ID` to inspect the next eligible ticket and `bugsnitch local-run --project PROJECT_ID` to run a bounded batch. Each attempt has a Git worktree, a configured edit scope and validator, and a separate review of the candidate revision. **Work** shows the last report, its machine and the next action. [Runner setup and execution](RUNNER.md)
3. **Ship the reviewed change.** The owner authorizes draft PR publication for the candidate and target. On the originating computer, `bugsnitch local-ship` can publish that branch using local GitHub credentials. In **Pull requests**, inspect the exact head, target, checks and reviews. Eligible repositories can opt into protected queue delivery. Once GitHub reports the merge, record the deployment handover for the environment and immutable build. [Pull-request workflow](INTEGRATION_QUEUE.md)
4. **Check what users get.** For an incident, record the fix, deployment and behavior check for the affected environment. A connected GitHub deployment monitor can receive signed deployment and check events. A passing verdict requires matching evidence for the active build. Missing observations leave the outcome unresolved. [Environment verification](PROVIDERS.md#environment-verification)

A workspace has one owner who manages access, repository connections, policies and capacity. Named operators can report incidents and inspect pull requests. Named approvers can also approve plans, answer current decisions, attach PR evidence, sign off on integration and record deployment handovers. Member access can cover one project or the workspace. [Dashboard walkthrough](DASHBOARD.md)

The dashboard and ChatGPT tools read the same workspace records. The runner synchronizes status and bounded evidence, and the owner can explicitly share a candidate diff. Local paths, runtime credentials and full execution artifacts stay on the runner. Selected task context goes directly to the configured model provider during a locally initiated turn. [Model access](CODEX.md) · [Integrations](INTEGRATIONS.md)

To try the delivery sequence without provider accounts, run `make checkout-acceptance` from the repository root. The exercise uses a scripted repair, fixture provider messages and a real browser check against the locally deployed checkout.
