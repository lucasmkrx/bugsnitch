# Version 1 transport

Use the same origin as the service for browser requests. JSON request bodies on the owner and device routes are bounded to 64 KiB. The Web UI signs in with POST /api/v1/login and refreshes GET /api/v1/state. The latter contains recent owner-scoped records, device last contact and a snapshot timestamp. Resource versions are checked again when a mutation runs. HTTP 202 means an intent was accepted.

Device protocol structs live in internal/protocol/device.go. POST /api/v1/device/pair redeems an expiring code for a name and selected projects. A device persists its own random credential before first transmission; replay of the same grant and credential recovers the enrollment. POST /api/v1/device/sync accepts at most 64 versioned reports and 64 acknowledgments. The response includes typed pending commands. A disconnected runner can replay the latest snapshots. POST /api/v1/device/admission handles locally initiated ticket and model-turn reservations, with one sequence per attempt and no expiry based solely on heartbeat. Protocol mismatch returns 426.

POST /api/v1/plans proposes an immutable plan (projectId, project version and plan document). POST /api/v1/plans/{id}/approve binds scope to the reviewed project version. POST /api/v1/plans/{id}/evidence records the owner's affirmative acceptance of an integrated issue with number, revision and summary. The schema and feasibility checks are in internal/domain/plan.go.

An owner can set an enrolled device's hosted model-turn limit with `POST /api/v1/devices/{id}/limits`. Send `turns` (1–32) and the current `limits.version` from `GET /api/v1/state`. A successful response contains `turns` and the new `version`. The same version guards workspace and device capacity changes. The snapshot includes `turnLimit` on each device.

A foreground batch may send `waitForTurn: true` in `POST /api/v1/device/next` to request a ticket while all model turns are occupied. Selection still checks ticket capacity, plan dependencies and resource conflicts. Every model turn requires a separate successful admission. A model-turn capacity conflict on the admission endpoint returns HTTP 409 with `code` set to `model_turn_capacity`.

If the original device stops locally with an unacknowledged `turn_start` at sequence S, it records that outcome and sends `turn_abandon` at S+1. The server accepts this operation whether the start committed or is still in transit. It frees any matching model turn, rejects a delayed start at S and retains the ticket until `finish`. The device can replay the abandonment after a lost acknowledgement, including while dispatch is paused.

GET /healthz reports process liveness. GET /readyz probes PostgreSQL through the public server’s Rust coordinator and the private domain worker. Webhooks use POST /hooks/github and /hooks/sentry. MCP uses /mcp. Each HTTP response carries an X-Request-ID. Error responses omit request contents and credentials.

For a plan that needs new GitHub tickets, stage a publication with POST /api/v1/publications carrying projectId, requestId, the current project version and a plan document. Its numbers are provisional dependency keys until publication finishes. POST /api/v1/publications/{id}/approve with the publication version authorizes creating issues in the configured GitHub installation. The outbox resolves prerequisite links into canonical GitHub numbers before posting each dependent issue. The final canonical plan is a new proposal requiring execution-scope approval. GET /api/v1/state includes the publication status, durable per-issue write state and canonical mapping. Reconciliation after an ambiguous write uses a stable App-authored marker. Exhausted reconciliation remains blocked for owner inspection.

The service accepts typed device rotation, worker lease renewal and general model permits in addition to device sync. The rotation recovery window is 24 hours. Keep issued credentials out of shell history and application logs. Shared diff content is available only via the scoped GET /api/v1/attempts/{id}/diff endpoint after local approval; snapshots carry digest and revision metadata. Workspace emergency stop is POST /api/v1/workspace/dispatch with stopped, version and requestId. GET /api/v1/state reports workspace.dispatchVersion and workspace.stopped.

## Event attribution

An owner session can page through its workspace history with `GET /api/v1/events?after=0&limit=50`. The response contains `events` in ascending order, `nextCursor` as a decimal string, and `hasMore`. The page size defaults to 50 and accepts 1 through 150. Store the returned cursor after consuming a page, and reuse it on reconnect. An empty page returns the supplied cursor. Each record has a `cursor` specific to its workspace and a historical `seq` event ID. The dashboard snapshot lists the newest 150 in descending cursor order.

The owner-scoped `GET /api/v1/state` returns audit metadata in `events[]`. Each record keeps its event kind, subject, workspace scope, sequence and timestamp. `actorSource` identifies an owner session, authorized plugin grant, registered device, background service or signed provider. The wire values are `owner`, `plugin`, `device`, `service` and `provider`. `actorId` identifies the resolved account, grant route, device, component or provider installation. A plugin grant identifies an authorization route shared by its callers.

`reason` is a bounded operational explanation or validated decision option. `policyVersion` identifies the project policy used for that operation when recorded. `subjectVersion` identifies the revision checked or recorded for that event. `evidenceRef` points to the event-specific incident inbox row, decision, command, digest, commit or provider identity. Missing fields and historical attribution are JSON null. Pairing and bearer credentials are excluded. Attribution comes from the authenticated execution path. Client-provided attribution headers have no effect.
